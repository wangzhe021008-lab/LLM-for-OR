# 数据字段和转换口径（模型版本 1.0）

本文件是本项目的显式实现约定；原始输入来自 `data/raw/Dataset - Prins LRP original instances and adapted instances.xlsx`，模型定义来自 `models/model_catalog.json`。每个标准化实例另保留具体单元格来源。此说明不是新增数学模型。

## 节点和需求

工作表 A 列区分仓库 `d1` 等与客户编号，B/C 列为坐标，D 列对仓库代表容量 U，对客户代表正需求 q。E 列为仓库开放成本 F。最终节点编号必须以标准化实例为准，不能自行改名、漏客户或增加客户。M1 使用所有候选仓库，M2/M3/M4 只使用场景明确允许的开放仓库。若只想服务部分客户，需要新的明确实例，不可在映射阶段静默删除其他客户。

## 车辆容量

按标签 `vehicle capacity` 读取 Q；`70/150` 表示两个候选实验容量，不是分数，不是混合车队。准备程序会产生容量明确的实例。业务未指定容量版本时必须澄清。按标签 `opening cost of a route (cost of a vehicle)` 读取每条路线固定成本 h。

## 路段成本

从坐标计算欧氏距离 dist。原表 `route cost type` 为 0 时，行驶成本 `c[u,v] = floor(100 * dist[u,v])`；为 1 时，`c[u,v] = dist[u,v]`。成本矩阵不是已确认的物理公里矩阵。非负数截断等同向下取整。

## 整单成本

M1/M2 按固定独立直送口径预计算 `g[d,i] = h + c[d,i] + c[i,d]`。g 是整单配送成本，目标中不得再乘 `q[i]`。该口径不计算多客户合并路线节约，需检查每个客户需求不超过 Q。Q、h、c 是预处理依据，不是由 LLM 改写的优化决策。

## 开放与归属

M1 同时决定仓库开放和客户分配；M2 只决定客户分配。M3/M4 中仓库开放和每个客户所属仓库是外部给定输入。场景可以明确提供人工归属或引用上一阶段输出。程序先读取并验证引用结果，`reference_state.status=verified` 且包含可复用 `assignment` 时，完整归属已经存在，由 Python 精确继承；聊天摘要未展开不等于缺失，不要求用户重新手抄。确实缺失、重复、跨实例、超仓容或版本已变化时停止并说明具体原因。不得自动选择最近仓库；不得把无法识别的仓库当作新仓库。所有客户恰好一次归属，且所属仓库必须开放。

## 电动车字段

M4 中 `p` 来自 `Unit cost of electricity(C_e)`；`r0` 来自 `Electricity consumption per unit distance for an empty EV.(p'_0)`；`r1` 来自 `Electricity consumption per unit distance for a fully loaded EV(p'_*)`；`B` 来自 `EV_battery_capacity_MAX(kWh)=(QB_k)`。B 是能量容量，Q 是载重容量，二者不得混淆。柴油价格和燃油率不映射到 M4。不同工作表标签列不同，必须按标签读取。

## 物理距离

M4 必须由业务提供 `distance_scale_km`（每个坐标单位对应多少公里）及 `distance_scale_source`（口径确认来源），并采用与电耗率一致的距离单位：`ell[u,v] = dist[u,v] * distance_scale_km`。当前实现按公里匹配空载/满载电耗率；若实际数据的电耗距离单位不是公里，必须先确认并转换原始实例。原表整数成本规则不证明坐标单位就是公里，不得默认比例为 1 或把成本除以 100 当成已确认公里数。

## 载重电耗

M4 沿弧载重 f 对应 `E[u,v] = ell[u,v] * (r0*x[u,v] + (r1-r0)*f[u,v]/Q)`。需满足 `r1 >= r0 >= 0`，未选弧 x=f=0。每次满电出发、途中不充电；路线含回仓电耗。目标只包含出车固定成本与电费，不包含 M3 的另一个行驶成本项。

## 模板边界

M3/M4 当前不支持时间窗、取货、跨仓路线、途中充电、异型车队、比客户数更紧的车辆数上限。M4 当前不支持柴油、碳排放价格/上限、充电排队或电池衰减。输入表中存在这些列不表示模板已经支持。若业务要求这些功能，应标记 unsupported，不能悄悄忽略或添加公式。

## 数据与可行性

模型结构正确、JSON 格式正确都不等于实例可行。总仓容量足够只是必要条件，整客户分配必须进一步验证。M3 的独立往返路线在需求不超过 Q 且分组不超仓容时可构成基准。M4 还检查独立往返能耗；通过是充分可行基准，未通过不能直接断言无解。业务需要覆盖固定实例数值时，当前映射接口应要求补充明确数据或标记 unsupported，不支持静默改价、改容量。

## 数据在哪里、由谁读取

| 数据或规则 | 权威位置 | 使用方式 |
|---|---|---|
| 可选实例、源表、容量版本 | `data/processed/manifest.json` | 先定位确切实例；同一工作表的 70/150 版本不能混用 |
| 原始数据 | `data/raw/` 下 manifest 指定的工作簿 | 导入来源由 `workbook_sha256` 标识，原表保持不变 |
| 规范化参数与单元格来源 | `data/processed/instances/{instance_id}.json` 中 D/C、q/U/F、Q/h、coordinates、ev、source_cells | Python 读取和计算，LLM 不抄矩阵；source_sheet/source_cells 可追溯原表 |
| 原表单元格快照 | `data/processed/source_sheets/{source_sheet}.json` | 用于检查导入来源与保留的公式/缓存值 |
| 前序仓库和客户归属 | 被引用结果的 `summary.json` / `mapping.json` | 本轮重新检查完整性、唯一性、仓库容量与实例一致性，验证通过后精确绑定 |
| 数据、模型版本与参数修改 | 被引用结果的 `binding_state.json` | 核对修订号与指纹；不能让旧归属默默套用已变数据 |
| 完整数学模型与输入接口 | `models/model_catalog.json`、`models/M*.py`、`schemas/M*.schema.json` | 系统直接读取；知识检索不决定目标或约束是否存在 |

文件路径用于解释来源，不构成让模型执行任意文件访问的授权。真实数据由受控 Python 加载器读取。模型知识说明字段含义，不能代替实例数值、用户要求或真实前序决策。

## 会话延续的状态约定

本轮输入由四部分组成：当前用户原文、独立的历史对话、程序核验的引用状态、已核对的系统知识。最新原文更正优先；过去助手错误声称“缺少数据”不能覆盖实时检查。引用状态包含来源结果 ID、实例、完整客户分组、数据指纹和可复用范围。

本会话新完成的完整有效结果自动成为下一轮上下文；可以显式取消或改选。浏览历史报告不会改选。用户明确沿用后，程序继承必要输入；仅有上下文不意味着每次请求都强制固定旧仓库或旧归属。切换实例要重新判断，不迁移旧决策。

对明确保留客户归属的要求，程序建立 `inheritance_contract`，不能由聊天模型降为只保留仓库；这只是输入继承约束，不指定下一个数学模型。否定沿用、重新分配或互相冲突的描述不能套用此锁定。

局部参数更新继续使用白名单及修订校验，复用原模型；目前不把含参数修改的结果跨模型传递，以免修改丢失。M4 距离换算缺失、真正的数据缺项和不支持的业务要求仍须停止说明。

## 知识加载的完整性

聊天判断前加载已核对的 `runtime_contract.json`，把数据位置及会话读取规则提前交给模型。JEV 选型后再加载对应模型、版本的必需规则，以及完整模型定义和 Schema。`pack_manifest.json` 固定必需条目列表，`review_registry.json` 登记经工程核对的内容指纹。资料删漏、内容改动未核对、版本错配都不能静默通过。

日常映射始终先完整加载必需知识。若显式使用关键词或 Chroma 查询，其结果只是补充，不能用 Top-K 替换或裁剪必需规则。扩大知识库后也应区分必需契约与可选案例，不能把无关模型规则全部塞进当前请求。工程核对不是外部专家签字；完整加载也不证明语言模型理解必然正确。
